# StudyPulse: Фаза 3 — продуктовая стабилизация

## Главная цель Фазы 3

Превратить StudyPulse из рабочего учебного MVP в более понятный продуктовый интерфейс, где пользователю не нужно быть администратором собственной системы.

Сейчас приложение умеет много, но пользователь всё ещё должен вручную:

- создавать предметы;
- вносить расписание;
- добавлять задания;
- генерировать план;
- принимать план;
- перепланировать;
- синхронизировать;
- разбираться в технических статусах;
- видеть server URL, device UID, package ID и т.п.

Для продуктового приложения это неправильно.

---

## Принцип Фазы 3

```text
Меньше администрирования.
Больше автоматизации.
Меньше технических терминов.
Больше понятного пользовательского языка.
```

---

## Реалистичный объём Фазы 3

Учитывая ограниченное время, Фаза 3 сокращена до практически полезных вещей.

# Фаза 3.1 — Простой онбординг и профиль студента

## Цель

Сделать первый запуск понятным.

## Проблема сейчас

Новый пользователь попадает сразу в набор вкладок и не понимает, с чего начать.

## Что делаем

Минимальный онбординг на 3–4 экрана:

1. Приветствие.
2. Как тебя зовут?
3. Когда ты обычно учишься?
4. Разрешить напоминания?

После этого пользователь попадает на экран «Сегодня».

## Что добавляем

Простой профиль:

```text
displayName
studyStartHour
studyEndHour
defaultDailyMinutes
notificationsEnabled
autoPlanEnabled
```

## Что НЕ делаем

- регистрацию;
- email;
- password;
- OAuth;
- облачный аккаунт.

Это слишком сложно для текущего времени.

## Критерий готовности

```text
Пользователь после установки за 1–2 минуты понимает, что делать дальше.
```

# Фаза 3.2 — Автоматическое планирование

## Цель

Убрать ручные кнопки «Сгенерировать план» и «Принять план» из главного сценария.

## Проблема сейчас

Пользователь должен сам:

```text
Задания -> План -> Сгенерировать -> Принять
```

Это не продуктовый опыт.

## Что делаем

Приложение само:

- строит план при первом открытии дня;
- обновляет план после добавления/изменения задания;
- мягко перепланирует пропущенные слоты;
- сохраняет выполненные слоты;
- не трогает текущий активный слот.

## Пользователь видит

```text
Рекомендуемый план на сегодня
[Начать следующее]
[Изменить день]
```

## Что прячем

Ручные кнопки:

```text
Сгенерировать план
Принять план
Перепланировать
```

Оставляем их только в расширенных настройках / developer mode.

## Критерий готовности

```text
Пользователь добавил задание -> план появился сам.
```

# Фаза 3.3 — Очистка UI от технического жаргона

## Цель

Сделать интерфейс человеческим.

## Проблема сейчас

Пользователь видит технические вещи:

```text
Пакеты
Mock OCR
PROPOSED
PLANNED
MISSED
device UID
server URL
packageExternalId
```

Это нормально для разработки, но плохо для продукта.

## Что делаем

Переименовываем пользовательские термины.

Было:

```text
Mock OCR
```

Стало:

```text
Сканировать конспект
```

Было:

```text
PROPOSED / PLANNED / MISSED
```

Стало:

```text
Рекомендуется
Запланировано
Пропущено
Требует переноса
Выполнено
```

Было:

```text
Пакеты
```

Стало:

```text
Учебные материалы
```

или прячем совсем, если это demo-функция.

## Технические настройки

Переносим в раздел:

```text
Настройки -> Дополнительно -> Для разработчиков
```

Обычный пользователь не должен видеть:

```text
server URL
device UID
clientEventId
packageExternalId
raw JSON
```

## Критерий готовности

```text
В основном UI нет внутренних терминов базы данных.
```

# Фаза 3.4 — Фоновая синхронизация и простой backup

## Цель

Убрать кнопку «Синхронизировать» из главного сценария.

## Проблема сейчас

Пользователь видит:

```text
Очередь событий
Синхронизировать
Server URL
```

Это технический интерфейс.

## Что делаем

Синхронизация работает автоматически:

- при открытии приложения;
- при появлении сети;
- периодически через WorkManager;
- после важных событий.

Пользователь видит только мягкий статус:

```text
Прогресс синхронизирован
```

или при ошибке:

```text
Нет сети. Синхронизируем автоматически, когда связь появится.
```

## Backup

Делаем простой локальный backup:

- раз в сутки;
- или при крупных изменениях;
- в файл приложения;
- без сложного UI.

Пользователь видит в профиле:

```text
Резервная копия: сегодня
Восстановить
```

## Что НЕ делаем

- cloud sync;
- multi-device;
- end-to-end encryption;
- Firebase;
- Google Drive;
- настоящую авторизацию.

## Критерий готовности

```text
Пользователь не должен нажимать «Синхронизировать» вручную.
```

# Фаза 3.5 — Нормальные напоминания

## Цель

Сделать уведомления полезными, а не спамом.

## Проблема сейчас

Периодический Worker каждые 15 минут — грубое решение.

## Что делаем

Планируем конкретные напоминания:

- за 10–15 минут до учебного слота;
- за 24 часа до дедлайна;
- за 3 часа до критичного дедлайна;
- утренний дайджест, если включён.

Добавляем:

- тихие часы;
- отдельные каналы уведомлений;
- возможность отключить конкретный тип напоминаний.

## Что НЕ делаем

- push через Firebase;
- серверные уведомления;
- сложные action buttons, если нет времени;
- exact alarm без необходимости.

## Критерий готовности

```text
Уведомления приходят вовремя и не раздражают.
```

# Фаза 3.6 — Минимальная полировка виджета

## Цель

Сделать виджет полезным, но не перегруженным.

## Что делаем

Виджет показывает:

- дату;
- ближайший слот;
- количество карточек к повторению;
- риск дедлайна, если есть.

Добавляем обновление:

- при открытии приложения;
- после изменения плана;
- периодически.

## Что НЕ делаем

- интерактивный виджет со сложными действиями;
- несколько размеров, если нет времени;
- кастомные темы.

## Критерий готовности

```text
Виджет отвечает на вопрос: что делать ближе всего?
```

```text

```

# Вне объёма Фазы 3

Следующее сознательно откладываем, потому что это дорого по времени и риску:

```text
настоящий OCR;
настоящий ASR;
настоящий RAG;
векторный поиск;
облачные LLM;
импорт PDF;
Google Calendar API;
полноценная авторизация;
роли преподавателя/студента/администратора;
мультидевайс синхронизация;
групповой шеринг;
SQLCipher;
сложная аналитика;
CI/CD с релизами;
маркет-подготовка.
```

Это не значит, что это плохо. Это значит, что сейчас важнее сделать существующий продукт понятнее и автоматичнее.

# Итоговый приоритет Фазы 3

Если времени очень мало, делаем в таком порядке:

1. **3.0 Ветки и документация**
2. **3.1 Онбординг**
3. **3.2 Автоматический план**
4. **3.3 Очистка UI**
5. **3.4 Автосинхронизация**
6. **3.5 Напоминания**
7. **3.6 Виджет**
8. **3.7 APK**

Максимальный продуктовый эффект дадут первые четыре пункта:

```text
онбординг + автоплан + человеческий UI + фоновая синхронизация
```

Именно они превращают приложение из «набора функций» в «личный учебный ассистент».
